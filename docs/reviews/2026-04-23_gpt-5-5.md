# Production Readiness Review — GPT-5.5

Date: 2026-04-23

## TL;DR

Tokenizers is **not production ready for a broad public release yet**. The app has a promising local-first architecture, clear separation between assistant drafts and confirmed medication schedules, and a meaningful unit/widget test base. However, release-blocking issues remain around Android shipping configuration, network permissions, clinical safety posture, privacy/compliance documentation, and operational hardening.

A limited TestFlight-style pilot could be reasonable after the iOS build is verified, but I would not ship this as a production health/medication app until the P0/P1 items below are addressed.

## Scope reviewed

Reviewed repository structure, Flutter/Dart app code, persistence, AI integration, platform configuration, CI/CD, README, and tests under:

- `lib/`
- `test/`
- `android/`, `ios/`, `macos/`, `web/`
- `.github/workflows/`
- `codemagic.yaml`
- `pubspec.yaml`, `analysis_options.yaml`, `README.md`

## Positive findings

- **Good domain boundary:** the app separates UI, bootstrap, data, core domain, and feature modules reasonably well.
- **Local-first data model:** schedules, conversations, proposals, and adherence are persisted locally through Drift with an event log as source of truth.
- **Human-in-the-loop assistant:** Gemini output creates proposals rather than directly mutating confirmed medication schedules.
- **Reasonable testing base:** 24 test files cover domain logic, repositories, data reset, Gemini provider behavior, chat coordination, and key widgets.
- **CI exists:** GitHub Actions runs format, analyze, and tests on PRs/pushes to `main`.
- **API key handling is thought through:** native platforms generally use secure storage; web/macOS are explicitly treated as fallback storage.
- **Data reset exists:** Settings includes a guarded local delete flow and the reset service clears database rows plus AI settings.

## Priority findings

### P0 — Android production builds cannot use the live assistant

**Evidence:** `android/app/src/main/AndroidManifest.xml` only declares `RECORD_AUDIO`. `INTERNET` exists only in `debug` and `profile` manifests.

**Impact:** Android release builds will not be allowed to call Gemini, so the core assistant workflow fails in production even when a user has configured a valid API key. This is a hard blocker for Android release readiness.

**Recommendation:** Add `android.permission.INTERNET` to the main manifest and verify a release build can complete a Gemini request on a physical Android device.

### P0 — Android release signing is still debug-key based

**Evidence:** `android/app/build.gradle.kts` has:

```kotlin
release {
    signingConfig = signingConfigs.getByName("debug")
}
```

`codemagic.yaml` also comments out Android signing and Play publishing.

**Impact:** This is not shippable to Play Store/internal production distribution. It also creates a high-risk release-management path if debug-signed artifacts are shared outside development.

**Recommendation:** Configure a real release keystore through CI secrets, remove debug signing from release builds, and add an explicit Android release build/check to CI or Codemagic before considering Android production-ready.

### P1 — Clinical safety posture is not sufficient for medication tracking

**Evidence:** The app uses Gemini to parse medication changes and prescription/script photos, then allows users to confirm those proposals. There is no prominent medical safety disclaimer, emergency guidance, clinician/pharmacist verification prompt, or formal safety-review gate visible in the inspected code/docs. The system prompt asks the model to infer reasonable times when timing is missing.

**Impact:** Medication schedules are high-stakes. Even with explicit review, users may over-trust assistant-generated medication names, doses, timing, or prescription-photo extraction. For production, this creates patient-safety and liability risk.

**Recommendation:** Add product-level safety language and UX gates: “not medical advice,” “verify with your prescription/clinician/pharmacist,” emergency instructions, low-confidence/missing-field handling, and clear warnings before confirming medication changes. Consider disabling model inference for ambiguous dose/frequency fields and requiring manual confirmation of every clinically relevant field.

### P1 — Privacy/compliance story is incomplete for health data and AI calls

**Evidence:** README says local data is stored locally and Gemini requests are BYO-key, but there is no privacy policy, data processing notice, retention policy, consent flow, export/delete documentation beyond local reset, or App Store/Play privacy checklist. Health and medication data plus prescription photos can be sent to Google Gemini.

**Impact:** For a production health app, users need explicit disclosure of what data stays local, what data is sent to Gemini, what the third-party provider may process, and what platform-specific storage limitations mean. This is especially important for prescription photos and conversation history.

**Recommendation:** Add an in-app privacy notice and repository docs covering data categories, AI transfer, BYO-key implications, secure-storage limitations, local deletion scope, and compliance assumptions. If targeting regulated environments, define whether HIPAA/GDPR obligations apply and document the release posture accordingly.

### P1 — macOS and web API key storage fall back to non-secure storage

**Evidence:** `createPlatformApiKeyStore` returns `SharedPreferencesApiKeyStore` for `kIsWeb` and `TargetPlatform.macOS`. The settings copy warns that this is a fallback, but users can still store Gemini keys there.

**Impact:** Gemini API keys can be persisted in storage that is easier to extract than OS-backed secure storage. For production, this is a security concern, especially for a BYO-key app where leaked keys can incur user cost.

**Recommendation:** Prefer secure storage on macOS through Keychain-backed `flutter_secure_storage` if feasible. On web, avoid persistent API key storage or require explicit opt-in with strong warnings; consider session-only storage or a backend token broker if the threat model requires it.

### P1 — Model/provider error messages can expose sensitive details

**Evidence:** `GeminiModelProvider` throws exceptions containing raw Gemini response bodies, and `ChatCoordinator` stores `provider_error`, `provider_error_message`, and `stack_trace` in event payloads when model calls fail.

**Impact:** Provider responses and stack traces can include request/response details, model text, or debugging information that is not appropriate to persist in a health-data event log. Even local-only storage increases risk during device sharing, backups, diagnostics, or future sync/export features.

**Recommendation:** Store a sanitized error code/category for user-visible history and keep detailed diagnostics out of persistent app data unless a user explicitly opts into diagnostics. Avoid persisting stack traces in production builds.

### P1 — AI response parsing is not robust enough for production

**Evidence:** `GeminiModelProvider._tryParseDate` uses `DateTime.parse` directly, `_extractCandidateText` force-casts candidate fields, and proposal parsing assumes schema-conformant JSON. `ProjectionState` also uses direct `DateTime.parse` for stored date fields.

**Impact:** A malformed model response or corrupted event payload can crash the assistant flow or projection rebuild. In an event-sourced app, one bad event can repeatedly break projections until data is cleared or manually repaired.

**Recommendation:** Treat all model output and persisted JSON as untrusted: use safe parsing, collect field-level validation errors into `request_missing_info`, and make projection rebuild skip/quarantine malformed events rather than crash the app.

### P2 — No integration/end-to-end release tests

**Evidence:** The repo has 24 unit/widget tests but no `integration_test/` directory or automated device/browser flow tests. CI only runs `flutter test`.

**Impact:** Core production flows are cross-cutting and platform-sensitive: first launch, entering a Gemini key, sending a model request, attaching a prescription photo, confirming a proposal, marking a dose taken, deleting local data, and relaunching. Unit/widget tests are not enough to catch platform permission, storage, Drift web worker, or release-mode issues.

**Recommendation:** Add integration tests for the highest-risk flows on at least one native target and web. Add smoke tests for release builds where feasible.

### P2 — CI does not verify platform release builds

**Evidence:** `.github/workflows/ci.yml` runs format/analyze/tests only. Codemagic builds iOS only on tags. Android release is commented out.

**Impact:** Build/signing/runtime breakages can reach release time unnoticed. The missing Android `INTERNET` permission is an example that normal unit tests would not catch.

**Recommendation:** Add `flutter build web --release`, `flutter build apk --release` or app bundle, and an iOS build check in the appropriate CI/CD environment. Keep signed publishing separate, but verify release compilation continuously.

### P2 — Event log and projection rebuild may not scale indefinitely

**Evidence:** `DriftWorkspace.rebuild()` loads all events and fully deletes/reinserts projection tables after event changes. The event log stores conversation, proposals, model raw payloads, and adherence history with no compaction or retention strategy.

**Impact:** This is acceptable for early local-only usage, but long-term medication/adherence histories and conversations can grow. Full replay on startup or after writes may become slow and memory-heavy.

**Recommendation:** Add event counts/performance benchmarks, incremental projection updates, snapshotting, or retention/archival policies before scaling beyond pilot usage.

### P2 — Local database is not encrypted

**Evidence:** Drift opens a plain SQLite database (`driftDatabase(name: 'tokenizers_v0')`) with WAL enabled. Sensitive medication names, schedules, conversations, adherence events, and prescription-derived content are stored locally.

**Impact:** Device-level encryption helps on modern platforms, but app-level SQLite data can still be exposed through backups, compromised devices, local filesystem access, or shared desktop environments. For a health app, this should be an explicit product/security decision, not an implicit default.

**Recommendation:** Define the threat model. If stronger protection is required, evaluate SQLCipher/platform encrypted storage or limit what sensitive content is persisted. At minimum, document the current storage security clearly.

### P2 — Release model list includes preview/future model IDs

**Evidence:** `GeminiModel` exposes `gemini-3-flash-preview` and `gemini-3.1-pro-preview` in addition to `gemini-2.5-flash`.

**Impact:** Preview model IDs may change or be unavailable for some users/keys. This can create confusing production failures in Settings/Assistant.

**Recommendation:** For production, default to stable generally available models and hide preview models behind a developer/experimental flag unless availability is verified and failure UX is strong.

### P3 — Several large UI/application files are becoming hard to maintain

**Evidence:** Examples include `assistant_screen.dart` (~806 lines), `chat_coordinator.dart` (~888 lines), `settings_screen.dart` (~752 lines), and `today_screen.dart` (~666 lines).

**Impact:** This is not a launch blocker, but it increases regression risk as features grow. The app already has good feature folders, so extracting smaller widgets/controllers would fit the current architecture.

**Recommendation:** Gradually split large screens into private widget classes and move orchestration/state logic into focused controllers where it improves testability. Avoid broad rewrites.

## Security assessment

Current security posture is acceptable for an early prototype/pilot but not complete for production health data:

- Uses HTTPS for Gemini requests.
- Stores native mobile API keys through secure storage, but macOS/web use shared preferences fallback.
- Stores health data in local SQLite without app-level encryption.
- Sends conversation context, medication schedules, and optional prescription photos to Gemini when the assistant is used.
- Persists raw model/provider payloads and stack traces locally.
- Lacks formal privacy/compliance documentation and in-app consent/disclosure flows.

Top security fixes before production: Android networking/signing, sanitized error persistence, secure API key storage choices, clear privacy notices, and a documented local-data threat model.

## Code quality assessment

Overall code quality is better than a typical prototype:

- Feature-based structure is readable.
- Domain/application/data boundaries are mostly clear.
- Event sourcing is applied consistently.
- Tests cover several important domain and data paths.
- Lints are configured with useful additional rules.

Main maintainability concerns:

- Large widgets/coordinators need gradual decomposition.
- Model output parsing should be more defensive.
- Event replay should tolerate malformed historical events.
- Bootstrap naming still uses `Demo` even though README says fresh installs are not seeded; this is minor but can confuse release intent.

## Scalability and extensibility assessment

The architecture is extensible for a small local-first app:

- `ModelProvider` abstraction allows other AI providers.
- Repository interfaces separate the app from Drift.
- Event log supports auditability and projection rebuilds.
- Feature folders are a good base for expansion.

Scalability risks:

- Full event replay/reprojection after writes will eventually become inefficient.
- No sync/multi-device conflict model exists.
- No migration strategy has been exercised yet because schema is at version 1.
- Persisted raw payloads can grow storage quickly.
- Assistant/provider abstraction currently still assumes Gemini in settings and UX.

## Recommended ship gate

Before production release, require all of the following:

1. Android release manifest includes `INTERNET` and release builds are properly signed.
2. CI/CD verifies at least web and Android release builds; iOS release builds verified in Codemagic or equivalent.
3. Privacy notice and AI data disclosure are added in-app and in docs.
4. Medical safety warnings and confirmation UX are strengthened.
5. Model response parsing and projection replay are made defensive.
6. Provider errors/stack traces are sanitized before persistence.
7. Integration smoke tests cover first launch, AI key setup, assistant proposal, proposal confirmation, adherence logging, and data reset.
8. Storage/security decisions for local health data and web/macOS API keys are documented and consciously accepted or improved.

## Verdict

**Not production ready for broad public release.**

The app is a solid prototype or pilot candidate, particularly on iOS after verifying TestFlight builds, but Android cannot currently ship correctly, and the health/AI/privacy hardening expected for production is not yet in place.
